# Sprint 22F — Post-Import Processing Design

## 1. Purpose

Sprint 22F establishes the post-import processing layer for RIMS.

The controlled import services created in Sprints 22C and 22D are responsible for safely incorporating validated Schwab positions and transaction data into persistent RIMS storage.

Sprint 22F begins after those controlled imports succeed.

Its responsibility is to coordinate the existing RIMS analytical services so that the appropriate analysis is recalculated from the newly updated persistent data.

The post-import processing layer is an orchestration layer.

It does not become a new financial-calculation engine.

## 3. Goals

Sprint 22F will:

1. Coordinate post-import analysis after a successful controlled import.
2. Determine which analysis is affected by the imported data.
3. Use the existing RIMS analytical services.
4. Use the current persistent RIMS datasets as the source of truth.
5. Avoid duplicating financial calculations.
6. Return a structured processing result.
7. Preserve existing persistence boundaries.
8. Provide clear failure behavior.
9. Support independent positions and transaction imports.
10. Establish a clean handoff to Sprint 22G.

---

## 4. Non-Goals

Sprint 22F will not:

- parse Schwab CSV files;
- validate Schwab files;
- import positions;
- import transactions;
- replace existing controlled import services;
- modify transaction persistence rules;
- modify snapshot persistence rules;
- redesign income calculations;
- redesign forward-income calculations;
- build the Dashboard;
- add Dashboard financial logic;
- create a second transaction database;
- create a second snapshot database;
- create a new forward-income persistence system;
- automatically change forward-income assumptions;
- make investment recommendations;
- make trading decisions.

---

## 5. Existing Services Used

Sprint 22F will use the existing RIMS services rather than duplicating their calculations.

### 5.1 TransactionRepository

The transaction repository provides the authoritative persisted transaction dataset.

Relevant capabilities include:

- `all_transactions()`
- `income_transactions()`
- `recurring_income_transactions()`
- account filtering
- symbol filtering
- date-range filtering
- income totals

Post-import processing should obtain the complete transaction dataset through the repository.

It should not read individual transaction files directly.

---

### 5.2 IncomeAggregator

`IncomeAggregator` converts normalized investment transactions into an immutable `IncomeAggregationResult`.

It performs analytical aggregation only.

Sprint 22F will provide the transactions to the existing aggregator.

Sprint 22F will not duplicate aggregation calculations.

---

### 5.3 HistoricalIncomeAnalyzer

`HistoricalIncomeAnalyzer` analyzes an existing `IncomeAggregationResult`.

It produces historical income summaries and trends.

Sprint 22F will invoke the existing analyzer after transaction data changes.

The analyzer remains responsible for historical income calculations.

---

### 5.4 CurrentIncome

`CurrentIncome` analyzes historical income generated by securities currently held in the current portfolio.

It requires:

- the current `Portfolio`;
- the complete historical transaction tuple.

Sprint 22F will obtain both from the existing RIMS services and invoke `CurrentIncome`.

---

### 5.5 ForwardIncomeManager

`ForwardIncomeManager` coordinates:

- forward-income assumptions;
- the previous forward-income baseline;
- current portfolio holdings;
- forward-income analysis;
- change-reason detection;
- baseline persistence.

Sprint 22F will provide the current portfolio to the existing manager.

The manager remains responsible for forward-income calculations and baseline persistence.

Sprint 22F will not modify forward-income assumptions.

---

### 5.6 ControlledPositionsImportService

The controlled positions import service remains responsible for:

- validated positions input;
- source-file duplicate protection;
- Snapshot creation;
- Snapshot persistence;
- import lifecycle state;
- determination of whether the current portfolio advanced.

Sprint 22F will consume its successful import result.

It will not duplicate positions-import logic.

---

### 5.7 ControlledTransactionImportService

The controlled transaction import service remains responsible for:

- validated transaction input;
- source-file duplicate protection;
- transaction-level duplicate protection;
- transaction persistence;
- import lifecycle state;
- reporting transactions actually added.

Sprint 22F will consume its successful import result.

It will not duplicate transaction-import logic.

---

## 6. Processing Trigger

Post-import processing begins only after a controlled import has successfully completed.

A validation result alone is not sufficient to trigger post-import processing.

An import operation in `CONFIRMED`, `VALIDATION_FAILED`, or `IMPORT_FAILED` state does not constitute a successful import.

Only successfully imported data may trigger Sprint 22F processing.

---

## 7. Processing by Import Type

Positions and transactions affect different analytical layers.

### 7.1 Positions Import

A successful positions import changes the current portfolio.

Therefore a positions import should trigger:

1. Current portfolio retrieval.
2. Current-income analysis.
3. Forward-income management.

Historical-income analysis does not need to be rebuilt solely because positions changed.

The historical transaction dataset has not changed.

---

### 7.2 Transaction Import

A successful transaction import changes the historical transaction dataset.

Therefore a transaction import should trigger:

1. Complete transaction retrieval.
2. Income aggregation.
3. Historical-income analysis.
4. Current-income analysis.

Forward-income management does not need to run solely because transaction history changed.

The current positions have not changed.

---

### 7.3 Combined Processing

The UI permits positions and transaction files to be imported independently.

If both imports succeed during a workflow, post-import processing should be capable of processing the resulting combined state.

The processing layer must use the persistent state that exists after the successful imports rather than attempting to reconstruct state from the original CSV files.

---

## 8. Duplicate Transaction Imports

A transaction import can contain transactions that already exist in RIMS.

The controlled transaction import service reports:

- source transaction count;
- transactions added;
- duplicates skipped;
- income transactions added;
- recurring income transactions added.

Post-import processing must distinguish between:

1. a file that successfully imported and added new transactions;
2. a file that successfully imported but contained only transactions already present at the transaction level.

The processing layer must not create duplicate income merely because an import was attempted.

If no new transactions were added, the processing layer should avoid unnecessary transaction-driven recalculation where practical.

---

## 9. Current Portfolio Source

The current portfolio must come from the controlled positions import architecture.

The authoritative current portfolio is the successfully imported positions Snapshot with the latest Schwab reporting date.

Sprint 22F must not:

- choose the latest file based on filesystem modification time;
- choose the most recently imported file solely by import timestamp;
- reconstruct the portfolio from transaction history;
- read the Schwab positions CSV directly.

The existing controlled positions service already establishes this rule.

---

## 10. Transaction Source

The authoritative transaction dataset is the persisted `TransactionRepository`.

Sprint 22F must use:

    transaction_repository.all_transactions()

rather than:

- reading transaction CSV files directly;
- re-importing Schwab files;
- using only the transactions from the most recent import;
- reconstructing transactions from income records.

This ensures that historical analysis continues to include all successfully imported transaction history.

---

## 11. Historical Income Processing

When transaction data changes, Sprint 22F will:

1. Load all persisted transactions.
2. Pass them to `IncomeAggregator`.
3. Obtain an `IncomeAggregationResult`.
4. Pass the aggregation result to `HistoricalIncomeAnalyzer`.
5. Return the resulting `HistoricalIncomeResult`.

The processing layer does not persist the analytical result.

Historical income remains a calculated analytical view over persisted transactions.

---

## 12. Current Income Processing

When either positions or transactions change, Sprint 22F may need to recalculate current-income analysis.

The analysis requires:

- the authoritative current portfolio;
- the complete persisted transaction dataset.

Sprint 22F will invoke:

    CurrentIncome(portfolio, transactions).analyze()

The resulting `CurrentIncomeResult` is returned as part of the post-import processing result.

No separate current-income database is introduced.

---

## 13. Forward Income Processing

When positions change, Sprint 22F will invoke the existing `ForwardIncomeManager`.

The manager:

1. Loads forward-income assumptions.
2. Loads the prior baseline.
3. Builds current position states from the current portfolio.
4. Compares current states with the prior baseline.
5. Calculates forward income.
6. Applies change reasons.
7. Identifies closed positions.
8. Saves the new baseline.

Sprint 22F will not modify assumptions.

The manager's existing baseline persistence remains the authoritative forward-income state mechanism.

---

## 14. Persistence Boundary

Sprint 22F should not introduce a new analytical-results persistence layer.

The following remain persisted by existing components:

- Import operations;
- Positions Snapshots;
- Transactions;
- Forward-income assumptions;
- Forward-income baseline.

The following remain calculated results:

- IncomeAggregationResult;
- HistoricalIncomeResult;
- CurrentIncomeResult;
- ForwardIncomeManagementResult.

The exception is existing persistence performed internally by `ForwardIncomeManager`, specifically the forward-income baseline.

---

## 15. Result Object

Sprint 22F should return a structured immutable result representing the processing performed.

The result should identify:

- whether positions processing occurred;
- whether transaction processing occurred;
- whether historical-income analysis was performed;
- whether current-income analysis was performed;
- whether forward-income analysis was performed;
- the resulting historical-income analysis, when applicable;
- the resulting current-income analysis, when applicable;
- the resulting forward-income analysis, when applicable.

The result should also identify the source import identifiers that triggered processing where appropriate.

The result should not contain duplicated financial calculations.

---

## 16. Processing Coordinator

Sprint 22F should introduce a dedicated service responsible for orchestration.

The service should have dependencies injected into it rather than constructing unrelated global state internally.

The coordinator should:

1. Receive a successful controlled import result or explicit processing request.
2. Determine which analytical layers are affected.
3. Retrieve authoritative persisted data.
4. Invoke existing analytical services.
5. Return the structured result.
6. Propagate processing failures clearly.

The coordinator should not perform financial calculations itself.

---

## 17. Failure Handling

Post-import processing failure is distinct from import failure.

Example:

    Controlled Import
          |
          v
       IMPORTED
          |
          v
    Post-Import Processing
          |
          X
       Processing Failure

In this situation:

- the underlying import remains an `IMPORTED` operation;
- persisted imported data is not falsely marked as missing;
- the processing exception must be visible to the caller;
- the processing result must not be reported as successfully completed.

Sprint 22F must not silently convert processing failure into import failure.

Sprint 22G will address broader recovery and reconciliation behavior.

---

## 18. Atomicity Boundary

Sprint 22F does not make the entire import-plus-analysis process one database transaction.

The controlled import services establish their own persistence guarantees.

Post-import analysis operates after successful persistence.

If analytical processing fails:

- previously imported persistent data remains intact;
- the import operation remains evidence that the source data was successfully imported;
- processing status must be observable through the returned result or exception.

Future recovery/reconciliation mechanisms belong to Sprint 22G.

---

## 19. Idempotency

Sprint 22F should avoid creating duplicate persistent data.

Analytical calculations themselves are naturally repeatable because they operate on the authoritative persisted datasets.

The primary stateful exception is forward-income baseline management.

The existing `ForwardIncomeManager` controls baseline updates.

Repeated post-import processing should therefore:

- not duplicate transactions;
- not duplicate snapshots;
- not create duplicate income records;
- use existing transaction and snapshot persistence rules;
- allow forward-income baseline management to remain under the existing manager.

---

## 20. Scope of Recalculation

Processing should be driven by what changed.

### Positions changed

Run:

- Current Income
- Forward Income

Do not require Historical Income solely from the positions change.

### Transactions changed

Run:

- Historical Income
- Current Income

Do not require Forward Income solely from the transaction change.

### Both changed

Run:

- Historical Income
- Current Income
- Forward Income

This minimizes unnecessary processing while preserving analytical correctness.

---

## 21. Dashboard Boundary

Sprint 22F does not connect the Streamlit Dashboard.

The Dashboard currently contains placeholder "Not Connected" metrics.

Those placeholders are intentionally outside Sprint 22E and remain outside Sprint 22F.

The Dashboard will consume established RIMS services after the post-import processing architecture is stable.

Dashboard integration should be addressed in a subsequent sprint.

---

## 22. Testing Strategy

Sprint 22F tests should include:

### Unit tests

- positions-only processing;
- transactions-only processing;
- combined processing;
- no unnecessary processing for unaffected layers;
- current portfolio retrieval;
- complete transaction retrieval;
- historical income orchestration;
- current income orchestration;
- forward income orchestration;
- structured result contents;
- processing failure propagation;
- no persistence of analytical results by the coordinator.

### Integration tests

At minimum:

1. Successful positions import followed by post-import processing.
2. Successful transaction import followed by post-import processing.
3. Successful positions and transaction imports followed by combined processing.
4. Duplicate transaction import does not duplicate income.
5. Processing uses persisted data rather than source CSV files.
6. A processing failure does not falsely change a successful import to `IMPORT_FAILED`.

---

## 23. Acceptance Criteria

Sprint 22F is complete when:

1. A dedicated post-import processing coordinator exists.
2. It does not perform financial calculations itself.
3. Positions changes trigger current-income and forward-income processing.
4. Transaction changes trigger historical-income and current-income processing.
5. Combined changes trigger all applicable analysis.
6. The current portfolio comes from the authoritative Snapshot mechanism.
7. Transactions come from `TransactionRepository`.
8. Existing analytical services perform the financial calculations.
9. No duplicate transaction or income records are created.
10. Analytical results are returned in a structured result object.
11. Processing failures are distinguishable from import failures.
12. Existing persistent financial data remains intact when analysis fails.
13. No Dashboard functionality is introduced.
14. Unit and integration tests cover the defined processing paths.
15. The full existing test suite continues to pass.

---

## 24. Sprint 22G Handoff

Sprint 22F establishes post-import processing.

Sprint 22G will address:

- end-to-end import/processing integration;
- reconciliation;
- failure recovery;
- incomplete processing detection;
- recovery after interrupted workflows;
- consistency between ImportOperation state and downstream processing;
- final Sprint 22 integration testing.

Sprint 22G should not require redesigning the analytical services established before Sprint 22F.

---

## 25. Design Principle

The central architectural rule for Sprint 22F is:

    Import safely.
    Process from authoritative persisted data.
    Reuse existing financial analysis.
    Persist only where an existing service already owns persistence.
    Do not put financial logic into the UI.
    Do not create duplicate sources of truth.

Sprint 22F is an orchestration layer, not another financial engine.
